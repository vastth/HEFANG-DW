## 4. 当前已冻结的关键决策

- Oracle 只读，不在 Oracle 新增对象或回写达播标记。
- 主方向已冻结为 MySQL / ODS 内部主线，不把“逐次直连 Oracle 桥接”作为最终日报方案。
- 当前统一 Excel 主路径下，`系统单号 = ods_m_retail.oms_sourcecode` 是主桥接路径。
- `平台单号` 只作为平台母单 / 追溯字段，不作为主桥接键。
- 当前 hefang_dw 内部优先承接对象是 `ads_dabo_order_label`，作用是给 ODS 订单打上“是否达播 / 达播渠道”的标签。
- `ads_dabo_daily_sales` 继续保留，不能为了日报主线把库存健康兼容链路拆掉。
- `ads_dabo_order_retail_bridge` 当前只作为应急兜底缓存，不作为优先主线。
- 统一 Excel 的筛选规则固定为：`平台` 划渠道、`状态 = 平台发货`、`主播名称` 非空且不以 `HEFANG` 开头。
- 旧 CSV 文件名前缀映射仅保留为历史兼容链路，不再作为当前筛选目标的主识别方案。
- 任何数据库写操作、结构变更、补数回填都必须由用户在当轮明确授权后才能执行。

## 5. 下一步计划

1. 先基于 [tools/extract_dabo_order_candidates_from_nas.py](../../tools/extract_dabo_order_candidates_from_nas.py) 与 [tools/load_dabo_order_labels_from_nas.py](../../tools/load_dabo_order_labels_from_nas.py) 稳定统一 Excel 输入契约与订单标签落表流程。
2. 以 `COALESCE(ads_dabo_order_label.canonical_system_order_id, ads_dabo_order_label.system_order_id) = ods_m_retail.oms_sourcecode` 为主线做只读验证，并视结果决定缓存兜底逻辑是否进一步降级。
3. 如果用户要稳定交付日报，再把当前按标签过滤的查询模板收口为固定 SQL、固定导出脚本或固定落表方案。
4. 最后再决定旧 `ads_dabo_order_bridge` / `ads_dabo_daily_sales` 的兼容治理范围。

## 6. 待业务确认问题

- 达播日报最终交付形态是什么：临时查询、固定导出，还是要进入新的 ADS / 报表对象。
- `ads_dabo_order_label` 是否成为 hefang_dw 内部唯一主标签对象，还是后续仍需与 `ads_dabo_order_bridge` 双存。
- `ads_dabo_order_bridge` 是新增 `system_order_id / platform_order_id` 字段，还是迁移既有 `main_order_id` 语义。
- 旧 CSV / 前缀兼容链路是否还需要继续维护，以及维护到什么阶段。
- 当 ODS 覆盖率继续提升后，是否要正式下调缓存兜底方案的优先级或停止维护。
