## 2. 本任务的真实目标

- 真实目标不是继续使用 CSV 里的商家收入金额直接出报表。
- 当前冻结的业务目标，是先从云雀导出的 `订单管理*.xlsx` 中筛出“达播订单集合”，并在 hefang_dw 内落一张订单标签表，为 ODS 订单打上“是否达播、属于哪个渠道”的标签；后续再复用现有 ODS 销售数据，按 ODS / Oracle `BILLDATE` 统计“每天实际发生的达播实收 / 退款 / 净额”。
- 该链路必须保留现有 `ads_dabo_daily_sales` 兼容输出，不能破坏库存健康链路。

## 4. 已确认的关键业务结论

- Oracle 侧保持只读，不能在 Oracle 新增对象、回写达播标记或执行任何增删改。
- 统一 Excel 的达播筛选规则已经冻结：
  - `平台` 划渠道
  - `状态 = 平台发货`
  - `主播名称` 非空，且不以 `HEFANG` 开头
- 当前最稳的主桥接键，不再是泛化的“主订单编号”概念，而是：`系统单号 = ods_m_retail.oms_sourcecode`。
- `平台单号` 只保留为辅助字段，用于平台母单追溯、排障或回查，不承担主桥接职责。
- 用户对整份云雀 Excel 扫描发现 `268` 行 `平台单号` 与 `系统单号` 不一致；这些 `系统单号` 普遍带有 `-3051286`、`-3051291`、`-C1`、`-C2` 等后缀。拿这些差异样本去 Oracle `BOSNDS3.M_RETAIL` 只读核查后，`系统单号` 稳定命中当前业务单据，而裸 `平台单号` 要么命中更早历史单据，要么完全不命中。
- 日报口径不是 Excel 自带收入，而是 ODS 零售单据的 `BILLDATE` 口径。
- 销售 / 退款识别沿用既有销售逻辑：
  - `TOT_AMT_ACTUAL > 0`，或单头为 0 但明细 `qty > 0`，视为销售。
  - `TOT_AMT_ACTUAL < 0`，或单头为 0 但明细 `qty < 0`，视为退款。
- `ods_m_retail.oms_sourcecode` 在 MySQL 侧必须按较长订单号场景保留足够长度，当前实现按 `VARCHAR(512)` 方向处理。
- 当前公司环境下默认只有用户本人可对数据库做最终执行和落库决策，不能假设存在内部 DBA / 运维协同路径。

## 5. 已确认的架构决策

- 当前落地顺序已调整为 hefang_dw 内部优先：先在本仓库落一层“统一 Excel 候选集提取工具”，把输入契约稳定下来，再决定是否迁移旧 `ads_dabo_order_bridge` 语义。
- 统一 Excel 主路径下，平台来源应以 Excel 行内 `平台` 字段为准；旧文件名前缀映射只保留为历史兼容链路，不再作为当前筛选目标的主识别方案。
- hefang_dw 当前内部主承接对象优先改为 `ads_dabo_order_label`：先解决订单打标，不把 Excel 金额字段兼容当成当前主阻塞项。
- 旧达播兼容链路当前仍保留，但不会阻断统一 Excel 主线先落标签表。
- 若后续要正式落库，订单桥接明细应显式保留 `system_order_id` 和 `platform_order_id` 两套字段语义，避免再次把辅助字段当成主桥接键。
- hefang_dw 主方向已回到 ODS 内部主线：优先用 `ads_dabo_order_bridge.system_order_id = ods_m_retail.oms_sourcecode` 做桥接，不把“实时去 Oracle 逐单桥接”作为默认日报主路径。
- Oracle 只用于只读验证、补证或 ODS 证据不足时的核查，不承担任何写入或中间表落地职责。
- `ads_dabo_order_retail_bridge` 仍保留，但当前定位已经降级为应急兜底缓存，不是主线依赖对象。
- 后续任何 DDL / DML / 建索引 / 回填 / 批量修数动作，除非用户在当轮明确授权，否则 Agent 只负责给出 SQL 或脚本，不直接执行。

## 7. 已核验的数据库事实

- 2026-03-31 的只读 MySQL 复核结果：
  - `ods_m_retail` 总行数 `1,859,358`
  - 其中 `oms_sourcecode` 已填充 `1,097,181` 行
  - `oms_sourcecode` 仍为空 `762,177` 行
  - 样本 `dabo_20260204.csv` 的 `cache_only_orders = 0`，说明旧抖音样本已可走 ODS 主线
- 2026-04-08 的统一 Excel 真实样本核验结果：
  - 整份 Excel 中有 `268` 行 `平台单号 != 系统单号`
  - `6924639914841439798-3051286` 命中 Oracle 2026-03-27 单据 `RE2603270000141`，裸平台单号 `6924639914841439798` 只命中更早的 2026-03-05 单据 `RE2603050001866`
  - `6951493917365049300-3051291` 命中 Oracle 2026-03-27 单据 `RE2603270000142`，裸平台单号只命中更早的 2026-03-22 单据
  - 淘宝样本 `2701769666144032793` 裸平台单号不命中，只有 `2701769666144032793-C1` 能命中 Oracle

说明：

- 上述差异样本已经足以把主桥接键冻结为 `系统单号`，不再建议继续以 `平台单号` 做默认桥接假设。

## 8. 尚未最终确认的问题

- 统一 Excel 的内部候选集接入已在当前仓库落地，但旧 CSV 兼容链路后续保留范围仍待确认。
- `ads_dabo_order_label` 已有骨架，但还未在用户授权下正式写库，也未接入固定调度。
- `ads_dabo_order_bridge` 是否直接新增 `system_order_id / platform_order_id` 字段，还是通过迁移当前 `main_order_id` 语义来完成模型收口，尚未最终定案。
- 当前日报结果已可查询，但是否要继续产品化为固定落表、固定任务或固定导出物，还未进入实施阶段。
- `ads_dabo_order_retail_bridge` 应长期保留为应急缓存，还是在统一 Excel 主线稳定后进一步弱化，尚未最终决定。

## 9. 后续实现顺序建议

1. 先用 [tools/extract_dabo_order_candidates_from_nas.py](../../tools/extract_dabo_order_candidates_from_nas.py) 稳定 `订单管理*.xlsx` 的筛选逻辑与字段输出。
2. 用 [tools/load_dabo_order_labels_from_nas.py](../../tools/load_dabo_order_labels_from_nas.py) 先做 dry-run，再在用户授权后把结果写入 `ads_dabo_order_label`。
3. 在 hefang_dw 侧优先走 ODS 主线：`ads_dabo_order_label.system_order_id = ods_m_retail.oms_sourcecode`；Oracle 仅用于只读核验或补证。
4. 若用户需要按渠道统计生意额、退款等指标，优先基于标签表 + ODS 写 SQL 模板，不先要求 Excel 金额字段兼容。
5. 若未来发生新的桥接失败、字段歧义或平台例外规则，除了更新本目录文档外，还需要同步写入 `docs/AGENT_LESSONS.md`。

## 11. 一句话总纲

达播子项目的当前主方向，已经从“旧 CSV / 前缀驱动的桥接探索”收口到“统一 Excel 行级筛选 + 系统单号桥接 ODS / Oracle 销售主线”；现阶段最关键的冻结结论是：`系统单号` 才是 Oracle 主桥接键，`平台单号` 只保留为辅助追溯字段。
