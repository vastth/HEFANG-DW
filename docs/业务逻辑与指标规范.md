## 二、零售单业务逻辑

### 2.1 M_RETAIL单据生成时机

**线下门店：**
- 销售单：收银买单时生成（TOT_AMT_ACTUAL > 0）
- 退货单：顾客退货时生成（TOT_AMT_ACTUAL < 0）

**线上电商：**
- 销售单：仓库点击**发货出库**时生成（TOT_AMT_ACTUAL > 0）
- 退货单：仓库**确认收货**后生成（TOT_AMT_ACTUAL < 0）
- ⚠️ 发货前退款：**不生成任何单据**

---

### 2.2 关键结论

```
⭐ M_RETAIL的销售数量 = 实际出库数量（不是订单数量）
⭐ 用于计算周转天数时，用"销售数量"而非"净销量"
⭐ 因为退货的货物也需要先从仓库发出去，消耗了库存周转
```

---

### 2.3 销售数量提取SQL

```sql
-- 销售数量（出库数量，正向单）
SUM(CASE WHEN r.TOT_AMT_ACTUAL > 0 THEN ri.QTY ELSE 0 END) AS 销售数量

-- 退货数量（入库数量，负向单）
SUM(CASE WHEN r.TOT_AMT_ACTUAL < 0 THEN ABS(ri.QTY) ELSE 0 END) AS 退货数量

-- 净销量 = 销售数量 - 退货数量
销售数量 - 退货数量 AS 净销量
```

---

### 2.4 核心指标口径

| 指标 | 计算公式 | 数据源 |
|------|----------|--------|
| 销售额 | SUM(ri.TOT_AMT_ACTUAL) WHERE r.TOT_AMT_ACTUAL>0 | M_RETAILITEM |
| 销量 | SUM(ri.QTY) WHERE r.TOT_AMT_ACTUAL>0 | M_RETAILITEM |
| 退货额 | SUM(ABS(ri.TOT_AMT_ACTUAL)) WHERE r.TOT_AMT_ACTUAL<0 | M_RETAILITEM |
| 退货量 | SUM(ABS(ri.QTY)) WHERE r.TOT_AMT_ACTUAL<0 | M_RETAILITEM |
| 净销售额 | 销售额 - 退货额 | |
| 客单价 | 销售额 / 订单数 | |
| 退货率 | 退货额 / 销售额 | |

---

### 2.5 日报时间窗口口径

- 今日：固定取昨天，即 `SYSDATE - 1`
- 月累计：非每月1日时取本月1日到昨天；若今天是每月1日，则展示上一个完整自然月
- 同期累计：取去年对应同周期；若今天是每月1日，则展示去年的上一个完整自然月
- 示例：若今天是 2026-04-01，则月累计 = 2026-03-01 ~ 2026-03-31，同期累计 = 2025-03-01 ~ 2025-03-31

> 说明：该规则用于日报类统计，避免月初出现“本月1日大于昨天”而导致累计结果为 0。

---

### 2.6 门店经营日报口径冻结点

当前 `ads_store_daily_report` 已落为正式独立 ETL；销售部对外正式引用稿统一使用 [docs/销售部数据治理-子项目/store_daily_report_sales_rule_freeze.md](销售部数据治理-子项目/store_daily_report_sales_rule_freeze.md)。本节保留仓库级摘要，相关口径按以下事实冻结：

| 项目 | 当前口径 | 说明 |
|------|----------|------|
| 门店范围 | `dim_store_report_attr` 当前生效且 `is_include_in_daily_report='Y'` | 不再把门店名单写死在 SQL 里 |
| 商品范围 | 固定排除 `147=辅料`、`149=办公用品`、`150=道具`，其余 `dim_product.category_id` 默认纳入 | 新增 category_id 无需再补配置；`146=配件`、`148=辅销品`、`394=配饰` 当前继续纳入门店日报，不回写库存健康的主销品 12 类口径 |
| 交易明细 | `ABS(ri.tot_amt_actual) >= 1` | 当前冻结为绝对金额小于 1 的明细整体排除，以与业务对账侧一致 |
| 日销售额 / 月累计销售额 | 净额 | 退货负值直接冲减，不额外拆毛销字段 |
| 日销量 / 月累计销量 | 净量 | 退货负数直接冲减 |
| 日订单数 / 月累计订单数 | 净单数 | 基于日报有效交易集先按零售单去重，再按过滤后商品范围的单号净额判 `>0=1 / =0=0 / <0=-1`；`ABS(金额) < 0.0001` 视为 0，避免净零单被浮点残差误判 |
| 月客单价 | 非免税月累计销售额 / 总实际单数 | Tableau 门店明细总计行按 `SUM(IF is_duty_free='Y' THEN 0 ELSE mtd_sales_amt END) / SUM(mtd_order_cnt)` 重算；免税外部月累计销售额只参与月总达成，不进入月客单价分子 |
| 日/月折扣率 | 实际金额 / 吊牌金额 | 日口径使用当日销售净额 / 当日吊牌金额；月累计明细总计使用非免税月累计销售额 / 非免税月累计吊牌金额，必须先按免税标记过滤分子分母再聚合计算 |
| 销售额同比 | 同店同比 | 在源物理门店粒度以 `dim_store.open_date <= 去年同期月份第一天` 判定资格，再按最终经营实体汇总 `same_store_mtd_sales_amt / same_store_last_year_mtd_sales_amt - 1`；空开业日期判非同店并告警，不回退旧销售额规则；快闪仍排除纯同店 helper |
| 目标版本 | `target_date = report_date AND target_version = data_version` | 精确版本匹配，不自动兜底最新版本 |
| 月目标与日目标关系 | `month_target` 为当月固定目标；`day_target` 为按日冻结值 | 业务可按实际节奏动态调整日目标，因此月内 `day_target` 合计允许不等于 `month_target` |
| 共同考核主体 | 仅以 `门店考核归属` sheet / `cfg_store_assessment_assignment` 显式配置为准 | 不因同商场、同城市或 RT 编码自动推断共同考核 |
| 统计主体目标 | 优先取 `统计主体目标` sheet / `cfg_store_assessment_subject_target_daily` | 若未配置，则主体层回退为主体内门店目标求和 |
| 负责人映射快照 | 独立门店维护 `STORE`；共同考核经营体维护 `SUBJECT` | 若某共同考核经营体已存在，负责人快照中只保留经营体行，不再同时维护主店/快闪成员门店；负责人可为空，表示当前未分配 |
| 达成率空值 | 目标=0 返回 NULL；目标>0 且无销售返回 0 | 避免“有目标但没卖”被误写成 NULL |
| 目标配置缺口处理 | 目标配置行数少于有效门店数时只告警，不阻断 | 未来门店数量可能收缩，允许部分门店暂时无目标但保留日报行 |
| 排名 | `RANK()`，同分按 `store_id` 稳定排序 | 保证重复产出顺序稳定 |

|------|------|------|
| QTY | 库存数量 | 当前库存 |
| QTYVALID | 可用库存 | 扣除占用后 |

| QTYPURCHASEREM | 采购欠数/在途 | 已下单未到货数量 |

---

### 3.2 云仓机制（核心概念）

**什么是云仓：**
```
传统模式：线下门店库存只能门店卖
云仓模式：门店库存也可以给电商发货

好处：
- 提高库存周转
- 减少缺货
- 降低调拨成本
```

**如何识别云仓门店：**
```sql
-- C_STORE表中
IS_ALLO2OSTORAGE = 'Y'  -- 这个标识表示参与云仓
```

**何方珠宝云仓情况：**
- 云仓门店：48家
- 云仓库存：17.9万件
- 总仓库存：10.9万件
- **云仓比总仓还多！**

---

### 3.3 电商可售库存口径

**2026年1月13日会议确认**：

```sql
-- 电商可售库存 = 总仓 + 云仓
WHERE (s.CODE = '001' OR s.IS_ALLO2OSTORAGE = 'Y')
```

**为什么这样定**：
- 只算总仓：10.9万件
- 加上云仓：28.9万件
- 差异：+165%！
- 不加云仓会严重低估可售库存

---

### 3.4 库存分析常用SQL

```sql
-- 总仓+云仓库存汇总
SELECT
    SUM(fs.QTY) AS 总库存,
    SUM(CASE WHEN s.CODE = '001' THEN fs.QTY ELSE 0 END) AS 总仓库存,
    SUM(CASE WHEN s.IS_ALLO2OSTORAGE = 'Y' THEN fs.QTY ELSE 0 END) AS 云仓库存
FROM FA_STORAGE fs
LEFT JOIN C_STORE s ON fs.C_STORE_ID = s.ID
WHERE fs.ISACTIVE = 'Y'
    AND (s.CODE = '001' OR s.IS_ALLO2OSTORAGE = 'Y');
```

## 四、渠道与店仓编码

### 4.1 仓库编码规则

以下规则仅适用于 `C_STORE.CODE` 这一类店仓编码字段，不应直接外推到 `dim_channel.WING_CODE`。

| 编码 | 类型 | 说明 |
|------|------|------|
| 001 | 总仓 | 中山总仓，电商主仓 |
| 002-020 | 功能仓 | 旧款仓、返修仓等 |
| RT*** | 门店 | 如RT001=广州K11 |
| DS*** | 电商虚拟店 | 如DS001=天猫 |

**筛选SQL：**
```sql
-- 总仓
WHERE s.CODE = '001'

-- 线下门店
WHERE s.CODE LIKE 'RT%'

-- 电商渠道
WHERE s.CODE LIKE 'DS%'

-- 总仓+云仓
WHERE (s.CODE = '001' OR s.IS_ALLO2OSTORAGE = 'Y')
```

### 4.3 字段边界

| 字段 | 所属对象 | 当前语义 | 不能直接推出什么 |
|------|----------|----------|------------------|
| `CODE` | `C_STORE` | 店仓编码，遵循 `001 / RT*** / DS***` 规则 | 不能直接当作渠道主档编码 |
| `CODE` | `O2O_RETAIL_CHANNEL` | 渠道档案编码 | 不能直接当作店仓编码 |
| `WING_CODE` | `O2O_RETAIL_CHANNEL` / `dim_channel` | 渠道挂接码，当前按 Oracle 原值保留 | 不能直接假设一定等于 `DS001` 这类店仓编码 |

### 4.4 实操提醒

- 做库存、销售、渠道筛选时，若条件来自店仓维度，应优先用 `C_STORE.CODE` 或 `dim_store.store_code`。
- 做渠道主档核对时，应使用 `dim_channel.channel_id / channel_code / WING_CODE`，不要把 `DS***` 规则硬套到 `WING_CODE`。
- 2026-03-23 已实查 Oracle `O2O_RETAIL_CHANNEL` 与 MySQL `dim_channel`：两边均为 87 条记录，`WING_CODE` 全部非空，但不存在 `WING_CODE = DS001` 这一现网事实。

## 五、库存健康度指标

### 5.1 口径范围

**库存范围：**
- 来源表：dws_inventory_daily
- 口径：中山总仓 + 云仓门店
  - store_code = '001' 或 is_cloud_store = 'Y'
- 日期：ETL当天（snapshot_date）
- 说明：库存快照保留全量SKU，主销品类别过滤在ADS层统一控制

**销售范围：**
- 来源表：dws_sales_daily
- 口径：电商店仓 + 云仓门店
  - store_code LIKE 'DS%' 或 is_cloud_store = 'Y'
- 统计周期：
  - 近30天：date_id >= today-30
  - 近7天：date_id >= today-7

**达播销量范围：**
- 优先来源：最新 `ads_dabo_order_label` 批次 + ODS `ods_m_retail/ods_m_retailitem`
- 兜底来源：`ads_dabo_order_retail_bridge` 缓存；仅当标签批次不可用时回退 `ads_dabo_daily_sales`
- 口径：以订单标签识别达播订单后，对 SKU 粒度汇总正向销售数量与销售额
- 日期口径：标签主线使用 `billdate`，legacy 回退使用 `sale_date`，均与 `dws_sales_daily.date_id` 按自然日对齐
- 统计周期：同销售范围（近30天/近7天）

**SKU范围：**
- 来源表：dim_sku + dim_product
- 口径：仅保留有效SKU（sku_id 不为空）
- 类别：仅主销品类（M_DIM4_ID IN 134,142,139,138,141,143,133,136,140,137,144,145）

| natural_sales_qty_7d | 近7天自然销量 | sales_qty_7d - dabo_sales_qty_7d |
| natural_revenue_30d | 近30天自然销售额 | sales_amt_30d - dabo_revenue_30d |
| natural_revenue_7d | 近7天自然销售额 | 近7天销售额 - dabo_revenue_7d |
| return_qty_30d | 近30天退货量 | SUM(return_qty) |
| return_amount_30d | 近30天退货额 | SUM(return_amount) |
| daily_avg_sales | 30天日均销量 | sales_qty_30d / 30 |
| daily_avg_sales_7d | 7天日均销量 | sales_qty_7d / 7 |
| sales_velocity | 销售加速度 | (sales_qty_7d/7) / (sales_qty_30d/30) |
| natural_daily_avg_sales | 30天自然日均销量 | natural_sales_qty_30d / 30 |
| natural_daily_avg_sales_7d | 7天自然日均销量 | natural_sales_qty_7d / 7 |
| natural_sales_velocity | 自然销售加速度 | (natural_sales_qty_7d/7) / (natural_sales_qty_30d/30) |
| sales_trend | 销售趋势 | 见下方规则 |
| turnover_days | 周转天数 | total_qty / (sales_qty_30d/30)，若 30天销量为0，则为 9999 |
| inventory_status | 库存状态 | 见下方规则 |
| status_priority | 状态优先级 | 紧急缺货=1，需补货=2，正常=3，库存过高=4，滞销=5，停售=6 |
| suggest_qty | 建议补货 | 见下方公式 |

来源补充：`ads_inventory_health` 的达播字段自 2026-04-09 起优先使用最新标签批次，在 ODS 内按订单标签识别达播订单；若 ODS 尚无对应订单，则回退 `ads_dabo_order_retail_bridge` 缓存；仅当标签批次不可用时，才回退 `ads_dabo_daily_sales`。来源：[etl_ads_health.py](../etl_ads_health.py#L195)；[etl_ads_health.py](../etl_ads_health.py#L270)；[run_etl.py](../run_etl.py#L649)
| sku_grade | S/A/B/C | 见下方规则 |
| sales_rank | 销售排名 | 按 sales_amt_30d 降序 |
| sales_ratio | 销售占比 | sales_amt_30d / total_sales（%） |
| cumulative_ratio | 累计占比 | 累计 sales_amt_30d / total_sales（%） |

### 5.3 库存状态判定

| 条件 | 状态 |
| --- | --- |
| total_qty > 0 且 sales_qty_30d = 0 | 滞销 |
| total_qty = 0 且 sales_qty_30d = 0 | 停售 |
| 周转 < 30 | 紧急缺货 |
| 30 <= 周转 < 70 | 需补货 |
| 70 <= 周转 <= 90 | 正常 |
| 周转 > 90 | 库存过高 |

---

### 5.3a 销售趋势判定（sales_trend）

基于销售加速度 sales_velocity 判断：

| 加速度范围 | 趋势 | 说明 |
| --- | --- | --- |
| ≥ 1.3 | 快速上升 | 7天日均大幅超过30天日均 |
| 1.0 ~ 1.3 | 稳定 | 近期走量平稳 |
| 0.7 ~ 1.0 | 降温 | 近期销量趋缓 |
| < 0.7 | 快速下滑 | 7天日均大幅低于30天日均 |
| 无销售 | 无销售 | 30天销量为0 |

---

### 5.4 建议补货公式

```
suggest_qty = (90 - turnover_days) * daily_avg_sales - return_qty_30d - purchase_rem_qty
```

**补充说明：**
- 若 sales_qty_30d = 0 或 turnover_days >= 90，则 suggest_qty = 0
- 退货与采购欠数视作未来回补库存，需从建议补货中扣减
- **允许负数**：当suggest_qty < 0时，表示库存过剩（与Oracle逻辑一致）

---

### 5.5 SABC分级规则

- 评分口径：近30天销售额 sales_amt_30d
- 按 sales_amt_30d 降序计算累计占比（cumulative_ratio）

| 分级 | 规则 | 说明 |
| --- | --- | --- |
| S | 该SKU之前的累计占比 < 0.30 | 贡献前30%销售额的超级爆款 |
| A | 含该SKU的累计占比 ≤ 0.70 | 贡献30%~70%的核心款 |
| B | 含该SKU的累计占比 ≤ 0.90 | 贡献70%~90%的常规款 |
| C | 累计占比 > 0.90 或无销售 | 长尾/滞销款 |

> 说明：代码实际逻辑为S级用“该SKU之前累计”判断，A/B级用“含该SKU累计”判断，边界使用 ≤ 而非 <。

---

### 5.6 数据关联逻辑

**以库存表为主表**（与Oracle逻辑一致）：
```sql
FROM 库存汇总(总仓+云仓) AS 主表
LEFT JOIN 商品维度
LEFT JOIN 销售汇总(近30天)
```

- 包含所有有库存的主销品SKU（即使销售为0）
- 库存为0但有销售的SKU也会通过LEFT JOIN保留
- 不过滤QTY=0记录（FA_STORAGE中QTY=0仍表示该商品被管理）
