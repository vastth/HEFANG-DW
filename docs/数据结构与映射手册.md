**新增/注意字段（线下/线上口径差异）**

| 字段名 | 中文名 | 说明 |
|--------|--------|------|
| SETERID | 设置人ID | 线下收银/门店系统写入的操作人ID（线下通道常见） |
| SETTIME | 设置时间 | 线下收银/门店系统写入的时间（Oracle DATE 类型），线下订单多数填此字段而非标准审计字段 |

**口径说明**

- 线上订单（电商渠道）：标准审计字段 `CREATIONDATE` / `MODIFIEDDATE` / `MODIFIERID` 一般有值，`SETTIME/SETERID` 多为空。
- 线下订单（门店，`DOCNO` 或 `ORDERNO` 前缀含 `RT`）：标准审计字段常为空，但 `SETERID/SETTIME` 通常有值。

因此在做增量时需要兼顾两条写入链路，建议分别按 `MODIFIEDDATE`（线上）和 `SETTIME`（线下）做增量水位。

性能建议：为线下通道建立索引 `M_RETAILITEM(SETTIME, ID)` 以支持窗口查询。


### 1.7 O2O_RETAIL_CHANNEL（电商渠道）

说明：仓库内已补齐 [etl_dim_channel.py](etl_dim_channel.py#L1-L131) 与 [SQL/create_dim_channel.sql](SQL/create_dim_channel.sql#L1-L11)，用于把 Oracle `O2O_RETAIL_CHANNEL` 全量同步到 MySQL `dim_channel`；2026-03-23 已实查确认目标库现存 87 条记录与 Oracle 源表一致，`WING_CODE` 全部非空。来源：[etl_dim_channel.py](etl_dim_channel.py#L1-L131)

| 字段 | 当前可确认语义 | 说明 |
|------|----------------|------|
| ID | 渠道主键 | 对应 `dim_channel.channel_id`。来源：[etl_dim_channel.py](etl_dim_channel.py#L28-L31) |
| NAME | 渠道显示名称 | 如天猫、京东、抖音等渠道名称，对应 `dim_channel.channel_name`。来源：[etl_dim_channel.py](etl_dim_channel.py#L28-L31) |
| CODE | 渠道档案编码 | 当前脚本把它写入 `dim_channel.channel_code`；从仓库现有规则看，它不能直接等同于 `C_STORE.CODE` 的店仓编码。来源：[etl_dim_channel.py](etl_dim_channel.py#L28-L31)；[docs/业务逻辑与指标规范.md](docs/业务逻辑与指标规范.md#L211-L234) |
| WING_CODE | 渠道挂接码 | 当前脚本直接用它生成 `dim_channel.WING_CODE`；2026-03-23 实查表明该字段直接保留 Oracle 原值，现网并不体现为 `DS001` 这类店仓编码。来源：[etl_dim_channel.py](etl_dim_channel.py#L30-L32) |

**口径提醒**

- `C_STORE.CODE` 的店仓编码规则仍包含 `DS***` 电商虚拟店，如 DS001=天猫；但这套编码规则不能直接外推到 `O2O_RETAIL_CHANNEL.WING_CODE`。
- 因此在 `O2O_RETAIL_CHANNEL` 中，`WING_CODE` 应按 Oracle 原值理解；`CODE` 仍保留为渠道档案编码。
- 当前源表 87 条记录的 `WING_CODE` 全部非空，因此将目标字段重命名为 `WING_CODE` 并直接映射源表不会丢失现有渠道记录。

### 1.8 表关联关系

```sql
-- 核心关联SQL
FROM M_RETAILITEM ri
LEFT JOIN M_RETAIL r ON ri.M_RETAIL_ID = r.ID
LEFT JOIN M_PRODUCT p ON ri.M_PRODUCT_ID = p.ID
LEFT JOIN M_DIM d4 ON p.M_DIM4_ID = d4.ID        -- 类别
LEFT JOIN M_DIM d5 ON p.M_DIM5_ID = d5.ID        -- 性质
LEFT JOIN M_DIM d6 ON p.M_DIM6_ID = d6.ID        -- 系列
LEFT JOIN C_STORE s ON r.C_STORE_ID = s.ID
WHERE r.ISACTIVE = 'Y' AND r.STATUS = 2
```

**仓库筛选SQL：**
```sql
-- 中山总仓
WHERE s.CODE = '001'

-- 云仓（48家参与云仓的门店）

-- 总仓+云仓（电商可售库存）
WHERE (s.CODE = '001' OR s.IS_ALLO2OSTORAGE = 'Y')

-- 线下门店
WHERE s.CODE LIKE 'RT%'

-- 电商虚拟店
WHERE s.CODE LIKE 'DS%'
```

### 2.5 日期格式

伯俊ERP日期字段使用 **NUMBER(8)** 类型，格式为 **YYYYMMDD**：

```sql
-- 示例值
BILLDATE = 20260113  -- 2026年1月13日

-- 日期转换
TO_NUMBER(TO_CHAR(SYSDATE, 'YYYYMMDD'))  -- 当天
TO_NUMBER(TO_CHAR(SYSDATE-30, 'YYYYMMDD'))  -- 30天前

-- 月份筛选
WHERE BILLDATE >= 20260101 AND BILLDATE <= 20260131
```

### 3.7 ads_inventory_health（库存健康度）

这张表不从Oracle直接抽，而是在MySQL内基于dws层计算：

```
数据来源：
- 库存数据 ← dws_inventory_daily
- 销售数据 ← dws_sales_daily
- 达播销量 ← ads_dabo_order_label 最新批次 + ODS/缓存兜底（标签批次不可用时回退 ads_dabo_daily_sales）
- 商品信息 ← dim_product
- SKU信息 ← dim_sku
- 仓库信息 ← dim_store

计算内容：
- 周转天数 = 库存 / (30天销量 / 30)
- 库存状态（滞销/停售/紧急缺货/需补货/正常/库存过高）
- 状态优先级（紧急缺货=1…停售=6）
- SABC分级（按销售额累计占比）
- 销售排名/占比/累计占比（sales_rank/sales_ratio/cumulative_ratio）
- 建议补货 = (90-周转天数)*日均销量 - 退货 - 采购欠数
- 自然销量 = 全量销量 - 达播销量（用于自然销售加速度与趋势判断）
- 达播销售额/自然销售额：用于对比全量与达播口径差异

说明补充：自 2026-04-09 起，`ads_inventory_health` 的达播字段优先按最新 `ads_dabo_order_label` 批次桥接 ODS 订单，并对 `ods_m_retailitem` 汇总 SKU 30/7 天销量与销售额；若 ODS 尚无对应订单，则回退 `ads_dabo_order_retail_bridge` 缓存；仅当标签批次不可用时，才回退 `ads_dabo_daily_sales`。来源：[etl_ads_health.py](../etl_ads_health.py#L195)；[etl_ads_health.py](../etl_ads_health.py#L270)；[run_etl.py](../run_etl.py#L649)
- 运行链路：达播数据就绪时回填当日达播/自然字段
- 达播最新日期：用于识别达播数据滞后（按SKU统计）
```

### 3.7g ads_store_daily_report（门店经营日报）
