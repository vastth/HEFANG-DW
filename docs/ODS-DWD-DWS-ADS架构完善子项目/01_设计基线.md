## 3. 分层职责建议

| 层级 | 建议职责 | 禁止或限制事项 |
|------|----------|----------------|
| ODS | 保留源表原始字段、增量落地、水位与质量检查 | 不承载跨主题业务口径；不做复杂派生指标 |
| DIM | 维度标准化、编码映射、门店/商品/渠道等稳定维表 | 不承载事实明细金额、数量汇总 |
| DWD | 清洗后的明细事实层，沉淀统一过滤、状态、明细粒度、事实主键和跨主题可复用业务上下文 | 未验证前不接入总控；不直接面向 Tableau / ADS；不一比一照搬 ERP 导出 Excel 模板 |
| DWS | 基于 DWD + DIM 的主题汇总层，面向稳定分析主题 | 新主题原则上不再直接从 ODS 聚合，除非有明确例外说明 |
| ADS | 应用层、报表层、专题层，服务 Tableau / FineBI / Excel | 不重复承担 DWD 清洗职责；不擅自冻结业务口径 |

## 4. 非破坏式演进原则

1. **先旁路，后切换**：新增 DWD / DWS 先以独立脚本、独立参数、独立验证命令运行；验证通过前不写入 `STEP_ORDER`。
2. **先文档，后代码**：任何新 DWD / DWS 的粒度、主键、字段来源、增量窗口必须先在本文或主题设计文档冻结。
3. **先小窗口，后全量回填**：先用近 1 天或 7 天窗口做对账，再设计历史回填；不得未验证超时边界就接入主链。
4. **先并行验证，后替换旧表**：现有 `dws_sales_daily`、`dws_inventory_daily` 为生产可用主链资产，默认不原地破坏。
5. **写库由用户授权执行**：DDL、索引、回填、修数等写操作由用户人工执行，Agent 只提供 SQL / 脚本与顺序。
6. **DWD 不继承 DWS 的汇总过滤为唯一事实范围**：销售 DWD 不应只保留 SKU 非空行；库存 DWD 不应天然只保留总仓 / 云仓范围，这些过滤应在 DWS / ADS 或规则维表中显式表达。
7. **DWD 不是窄核算表，也不是单一 ADS 专用中间表**：销售 DWD 长期应承接会员、营业员、购物券、商品归因等关键业务上下文；库存 DWD 长期应保留全店仓库存快照事实，库存健康只作为第一批消费和验证场景。
8. **新架构不继承 Oracle 模板噪声**：raw ODS / DWD 草案字段必须同时满足真实有数据、语义明确、对新架构有价值；全量为 0 / 全量为空的 Oracle 模板化冗余字段不再为了追溯完整性保留。
9. **ADS 既有字段名属于外部消费契约**：当前 ADS 相关 MySQL 表已被 Tableau 和其他下游消费；影子链替代旧链时允许新增字段，但不得改名或删除既有 ADS 字段，避免消费层直接报错。

## 5. 推荐目标架构

```text
Oracle / HFSY / 文件源
        ↓
ODS：原始落地、增量水位、源侧质量检查
        ↓
DIM：商品、SKU、门店、渠道、日期等维度标准化
        ↓
DWD：销售明细事实、库存快照事实、会员事实、达播订单明细等（未实现，待分主题设计）
        ↓
DWS：销售日汇总、库存日汇总、会员主题汇总、达播主题汇总等（部分已存在，待逐步改造）
        ↓
ADS：库存健康、门店日报、销售专题、Tableau 应用层
```

## 7. DWD 主题设计模板

后续每个 DWD 主题落地前，必须至少补齐以下内容：

| 项 | 内容 |
|----|------|
| 主题名称 | 例如销售明细、库存快照、会员事实、达播订单明细 |
| 目标表名 | 暂定，必须标注“未实现”直到 DDL 用户确认并执行 |
| 业务粒度 | 一行代表什么业务事实 |
| 主键 / 唯一键 | 源侧稳定键或组合键，需证明可幂等 |
| 来源表 | ODS / DIM 表及字段来源 |
| 过滤规则 | 状态、有效性、门店、商品、退货等口径 |
| 增量策略 | 水位字段、回刷窗口、是否支持按日重算 |
| 幂等策略 | 删除重写、Upsert、临时表替换或分区替换 |
| 超时风险 | 数据量、事务范围、锁持有时长、`timeout_profile` 选择 |
| 验证方式 | 行数、金额、数量、主键重复、上下游对账 |
| 接入策略 | 是否旁路运行、何时可进入总控 |

## 8. 总控接入门禁

任何 DWD / 新 DWS 任务进入 `run_etl.py` 主链，或从 `scheduled_total_control.py` 的 shadow 观察态提升为阻断链路前，必须满足：

1. 有独立脚本与 `--conn-test` 或等效空跑能力。
2. 至少完成一次小窗口真实验证，保留命令、日志、耗时或查询结果证据。
3. 已明确 `timeout_profile`，并说明为什么选择 `default` / `etl` / `long_running`。
4. 已完成源侧 ODS → DWD → DWS → ADS 的最小对账。
5. 已同步根文档和本目录看板。
6. 用户确认可以接入主链。
7. 若涉及既有 ADS 表，已确认切换方案不改名、不删除现有字段，只在必要时新增字段，并已评估消费层兼容性。

## 9. 当前不做事项

| 不做事项 | 原因 |
|----------|------|
| 不直接修改 `run_etl.py` 增加 DWD 步骤 | 需要先完成设计、脚本、验证与用户确认 |
| 不直接改造 `dws_sales_daily` / `dws_inventory_daily` | 当前为现有调度链路依赖对象，不能破坏每日自动调度 |
| 不自动调整已建 raw / DWD / DWS v2 表结构 | 后续 ALTER、索引调整仍需用户人工执行或另行授权；M4 两张 DWS v2 表已由用户人工建表，Copilot 仅只读核验 |
| 不擅自执行数据库写操作 | raw / DWD 小窗口写入基于用户明确授权；后续 DWS v2 装载、回填、索引、修数仍需用户人工执行或另行授权 |
