# 项目目标与背景

---

## 1. 项目目标

本子项目目标是：在不影响当前每日总控自动调度的前提下，逐步补齐 DWD 明细事实层，并规范 DWS 主题汇总层，使后续新增销售、库存、会员、达播、渠道等主题时能够沿稳定分层演进，而不是继续让 DWS / ADS 直接承担 ODS 清洗、业务过滤、主题聚合和应用口径多重职责。

成功标准：

1. 当前生产可用的总控日调度不被破坏。
2. DWD 层的职责、粒度、命名、增量策略、验证方式先被文档冻结，再逐步实现。
3. 新 DWD / DWS 对象先以独立脚本、独立验证、独立回填方式落地，验证通过前不并入总控主链。
4. 每次推进后同步更新本目录文档，保证上下文压缩后仍可从文档恢复权威事实。

---

## 2. 背景

当前项目已形成 ODS、DIM、DWS、ADS 多层脚本与调度，但 DWD 层仍停留在架构规划层面。项目文档中已经给出 ODS → DIM → DWD → DWS → ADS 的理想分层图，但 DWD 示例表明确为“暂无（DWD层未在代码实现）”。证据：`docs/数据仓库与ETL手册.md#L52-L56`。

现有 DWS 主题脚本直接从 ODS 层读取并聚合：

- 销售 DWS：`etl_dws_sales.py` 注释说明“从MySQL ODS ods_m_retail/ods_m_retailitem 聚合到 dws_sales_daily”，SQL 中直接 `FROM ods_m_retailitem` 并 `JOIN ods_m_retail`。证据：`etl_dws_sales.py#L1-L4`、`etl_dws_sales.py#L56-L57`。
- 库存 DWS：`etl_dws_inventory.py` 注释说明“从MySQL ODS ods_fa_storage 聚合到 dws_inventory_daily”，SQL 中直接 `FROM ods_fa_storage`。证据：`etl_dws_inventory.py#L1-L4`、`etl_dws_inventory.py#L55-L55`。

这种结构短期可运行，但随着更多主题进入，会出现以下风险：

1. 同一 ODS 清洗规则在多个 DWS / ADS 中重复实现。
2. 销售、库存、会员、渠道等主题的明细粒度不统一，导致跨主题口径难追踪。
3. 后续补数和回刷时，无法清晰区分“明细事实修正”与“主题汇总重算”。
4. ADS 应用层容易直接继承 DWS 中临时口径，形成难以拆分的历史债务。

M1 只读审计后，背景进一步细化为：当前问题不只是“DWS 直接从 ODS 聚合”，还包括“当前保留的门店销售专题链路中，部分 ADS 已绕过 DWS 直接读取 ODS / 配置事实，而销售专题调度仍用 `dws_sales_daily.etl_time` 作为 freshness 代理”。库存健康 ADS 仍真实依赖 `dws_inventory_daily` 与 `dws_sales_daily`。证据：`etl_ads_health.py`、`etl_ads_store_daily_report.py`、`etl_ads_daily_sales.py`、`scheduled_store_daily_report.py`。

---

## 3. 当前调度现状

当前主链 `run_etl.py` 的 `STEP_ORDER` 包含：`dim_product`、`dim_sku`、`dim_store`、`dim_channel`、`ods_sync`、`dws_sales`、`dws_inventory`、`dabo_ready`、`ads_health`，未包含 DWD 任务键。证据：`run_etl.py#L52-L61`。

当前 ODS 增量主链默认回刷 7 天，DWS 销售主链窗口与 ODS 回刷天数保持一致。证据：`run_etl.py#L64-L65`。

当前总控 `scheduled_total_control.py` 已包含三个子链路：主链调度、门店销售专题，以及 `dws_v2_shadow` 非阻断观察子链；主链脚本路径仍为 `scheduled_etl.py`，后者统一调用 `run_etl.py` 的 `run_main()`。证据：`scheduled_total_control.py`、`scheduled_dws_v2_shadow.py`、`scheduled_etl.py#L48-L52`。

因此，本子项目的实施边界应理解为：在正式切换前不改 `run_etl.py` 主链任务顺序，不让未稳定的 DWD / DWS 新对象替换现有生产读源；若需要进入 `scheduled_total_control.py`，只能以独立 shadow 或非阻断子链方式观察运行。

## 4. 已知约束

| 约束 | 说明 |
|------|------|
| 不影响现有生产主链 | 新 DWD / DWS 在切换前不直接进入 `run_etl.py` 主链；若接入 `scheduled_total_control.py`，仅允许独立 shadow 或非阻断子链 |
| 数据库写操作由用户执行 | DDL、建索引、补数、回填、增删改数据仅由 Agent 输出执行方案，用户人工执行 |
| 必须保留证据 | 所有架构结论、字段映射、调度判断必须引用代码、文档、快照或实际查询结果 |
| 必须管理超时风险 | 后续涉及数据库读写的 ETL / SQL 必须评估数据量、事务范围、锁持有时长与 `timeout_profile` |
| 业务口径不得擅改 | SABC、销售净额、门店过滤、达播标签、会员识别等业务口径需要用户确认后才能冻结 |
