当前卡点
这为什么会卡项目

现在卡住的不是凭据，而是映射口径

主线登录与数据样本都已打通，但还不能把“支持第三方门店编码”直接当成当前租户已经配置完成。

  • `mobileLogin`、`getDepartments`、日级客流、小时客流都已经取到样本，说明接入主链不是账号问题。
  • 当前标准客流接口吃的是内部 `depId` 或 `S_门店id`；而第三方 `shopId` 字段在当前 64 家门店样本里仍为空。
  • 如果现在直接按“何方门店编码已在万店掌配置完成”去写 ETL，就会把未验证事实写死进模型，后续大概率返工。
  • 因此当前最小闭环不是再要密码，而是确认“何方门店编码 -> 万店掌 `depId` / `S_门店id`”的映射来源，并把完整 ODS/DWD/DWS/ADS 链路首轮跑通。
当前最小补料有两件：确认门店映射来源，并将已落盘的 ODS / DWD / DWS / ADS draft SQL 与脚本按小窗口完成首轮执行验证。若平台侧能补齐第三方店铺 ID，就继续验证 `shopId` 直连路径；若不能，就直接按内部 `depId` / `S_门店id` 维护映射表。

API 架构怎么工作的

把开发者控制台、应用级调用密钥、业务登录 token 分开看，问题就清楚了。

凭据域 A

开发者控制台账号

  • 用途：登录 docs.open.ovopark.com 控制台
  • 产物：控制台 ticket / cookie
  • 状态：已验证可用
凭据域 B

应用级 AccessKey

  • 用途：给 cloud.api 做 _sig 签名
  • 产物：合法的应用级请求
  • 状态：已验证可用
凭据域 C

业务账号密码

  • 用途：调用 mobileLogin
  • 产物：authenticator
  • 状态：已验证可用
运行结果

业务接口层

  • getDepartments 已成功返回 64 家门店
  • 客流接口已成功返回日级与小时级样本
  • 当前剩余问题是第三方门店编码映射
请求结构

网关请求长这样

  • Query 参数：_aid、_akey、_mt、_sm、_requestMode、_version、_timestamp、_sig、_format
  • 签名规则：参数按名字升序拼接，头尾加 AccessKey Secret，再做 MD5 大写
  • 业务接口额外要求：请求头带 authenticator
首登链路

正确推进顺序

  • 先用业务账号密码调用 open.shopweb.security.mobileLogin
  • 拿到 authenticator
  • 再调用 getDepartments 和客流接口
错误复用

现在已经排除的错误方向

  • 开发者账号 applicationKey 不能替代应用级 AccessKey
  • 控制台 ticket 不能替代 authenticator
  • 控制台登录密码不能默认等于 mobileLogin 密码
